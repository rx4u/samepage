# ADR-0009: Use a demo store as staging

Status: accepted
Date: 2026-11-06
Deciders: Claude (architect), agent call

## Context
Users' stores are private and never visible to the maintainer. Releases still need testing on every surface with production-sized data.

## Options

### Option A: A private `samepage-demo` store repo plus a Notion demo page, filled with generated synthetic data
- Pros: real connectors, real Action, real sizes; no user data.
- Cons: the maintainer keeps two demo stores current.
- Price: 0 USD.

### Option B: Unit tests on fixtures only
- Pros: fast.
- Cons: never exercises connectors, the Action or Claude Design.
- Price: 0 USD.

## Decision
Option A, plus fixtures for unit tests. The perf fixture defined in test-data.md is generated by `sp fixtures --perf` and pushed to the demo repo for release testing.

## Non-goals
Testing against any real user store.

## Consequences
- Gets easier: confident releases.
- Gets harder: release checklist has manual surface steps.
- Follow-up tasks: WP-04.

## Implementation plan
- Affected paths: sp/fixtures.py, fixtures/
- Pattern to follow: seeded random generation, same seed every release.
- Pattern to avoid: copying real projects into fixtures.
- Config and env changes: none.

## Verification
- [ ] `sp fixtures --perf --seed 42` produces the counts in test-data.md
- [ ] Release checklist records US-03, US-04, US-06 and US-07 passing on the demo store

## Revisit when
A contributor builds automated surface tests.
